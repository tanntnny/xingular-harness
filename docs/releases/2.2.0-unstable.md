# Xingular Harness 2.2.0-unstable

Unstable preview of the current Harness work. Install with `npm install @xingular/harness@unstable`.
This release adds the long-lived harness work on top of 2.1.0-unstable. It is a minor step because the
terminal's default changes: `xagent` now runs in the long-lived harness (ADR-0085). The package API and the
stored data layout are otherwise unchanged. **Tests were not rerun for this release commit, by request.** The
last full run before it (1,890 passed, 4 skipped; `npm run prove`; the terminal verifier) is in `HANDOFF.md`.

- **The long-lived harness is the default for `xagent` (ADR-0085).** A window runs in the daemon unless told
  otherwise: `--no-daemon` or `XINGULAR_DAEMON=0` keep a window's own harness. On Windows, with
  `XINGULAR_TERMINAL_RUNTIME=inprocess`, when the socket path is too long, or when the daemon cannot start, the
  window runs its own harness and says why. Asking for `--daemon` by name in one of those cases is an error.
- **Daemon robustness.** The lock is created whole and linked, records the folders and build, and a reused pid
  is recognised as stale. A start is logged to `harness.log` and fails fast. A killed window no longer holds the
  daemon or its worktree open, and a call after the socket closes rejects at once. `--worktree` works in the
  daemon.
- **A host's sessions are its own by the call that started them.** Side questions, refinements, subagents and
  probes a host starts are gated and heard by that host; a host that is briefly away is waited for (two
  minutes) and then fails closed; sign-in links go only to the call that asked for them. Every `daemon run`
  reads `<state>/host-launch.json`, so a terminal-started and a host-started daemon are the same daemon.
  `harness.open` of another data folder is refused while terminal windows use the harness.
- **A phone can control a host's live session (PAR-018).** `sessions.remoteControl.{start,stop,rotate,confirm,
  status,status.wait}`; a terminal window closed during a reply keeps its phone until the reply settles.
- **The daemon checks its version and exits when idle** (30 minutes). After an upgrade, a window replaces a
  daemon that nothing uses, or runs its own harness with a notice when something still does.

Known gaps: the agent's shell runs with the daemon's environment, not the window's (Known drift D-34; use
`--no-daemon` for work in another environment). A hung plugin in the daemon and a day-long soak with several
windows and the App have not been tested. No live model request was made.
