# Xingular Harness 1.0.0

This release establishes @xingular/harness@1.0.0 as the stable baseline and retains the xharness
command. It intentionally resets the earlier development numbering; historical tags and published
versions remain unchanged. The npm registry published 1.0.0 as the stable baseline; this file
remains its release notes.

## Included

- Pi execution with isolated accounts, pinned models/capabilities, gated tools and recorded usage.
- Foundation/variant architecture, validated c1–c8 variants, version history, continuation,
  answer-free refinement and opt-in lessons.
- Wiki notes, history/trajectory tools, MCP connectors, plugins, Hub installation and terminal UI.
- Generic web search/fetch and isolated browser tools, plus account and backend diagnostics in
  /doctor. Local inspection is the default; selected live probes require consent.
- Compiled Node ESM SDK and TypeScript declarations, including supported subpath imports.
- Apache-2.0 for original project code, with retained upstream attribution and license texts.

## Installation and requirements

Use `npm install --global @xingular/harness@1.0.0`, then `xharness`. Node 22.19 or later is required.
The terminal additionally requires Bun; release CI uses Node 22.19.0 and Bun 1.4.2. Browser operation
requires an installed compatible browser or a deliberately configured endpoint. Model credentials
are configured inside an isolated Harness account.

## Migration

- SDK tree symbols/paths become variant symbols/paths: VariantChoice, seedVariant, variant/*.
- Server harnesses.* methods become variants.*. Session/context inputs use variant; variant
  snapshots use variant and materialisation returns files. Old method aliases are not provided.
- Existing stored data is migrated without overwriting; historical run records remain readable.
- Versions numerically above 1.0.0 will not receive this release through higher-major semver ranges.
  Install the exact version or latest tag deliberately.

## Diagnostics limitations

Local readiness is not live connectivity. Doctor never signs in, switches accounts or repairs
settings. Provider probes may incur charges. Computer input remains blocked when the embedding
host cannot provide an isolated diagnostic surface. Runtime execution and compiled artifacts are
validated independently from publication; see the release checklist for actual gate results.
