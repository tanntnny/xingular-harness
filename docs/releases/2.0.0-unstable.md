# Xingular Harness 2.0.0-unstable

Unstable preview of the current Harness work. Install with `npm install @xingular/harness@unstable`.
This is a 2.0 line because the terminal's runtime changes: `xagent` is now a client of the harness
(ADR-0083), which adds methods and a socket transport and changes who owns execution in the
terminal. The package API and the stored data layout are otherwise unchanged.

- **One session runtime (ADR-0083): the terminal is now a client of the harness.** `xagent` runs no
  agent loop in its window any more. Each turn is a harness run with the same gate, run records,
  plan mode, goals and subagents as a host's, and the harness keeps the conversation's Pi session
  open across turns (`sessions.run { live: true }`), so steering, queued follow-ups and plugin
  state carry from one turn to the next. New methods `sessions.live`, `sessions.close`,
  `sessions.followUp` and `sessions.followUp.clear`. `XINGULAR_TERMINAL_RUNTIME=inprocess` runs the
  previous in-process runtime.
- **A long-lived harness (opt-in).** `xagent daemon start|stop|status` runs one harness per state
  folder on an owner-only socket; `xagent --daemon` windows use it, so a reply keeps running when
  its window closes, and `xagent attach [session]` reconnects. Plain `xagent` is unchanged: its
  window runs its own private harness.
- **Every harness run now ends when it stops making progress.** A reply that produces nothing for
  fifteen minutes (thirty with a tool running; a pending approval or a wait for subagents does not
  count) is interrupted with reason `stalled`, whatever front end started it, and its live session
  is closed rather than reused. Every run now sends the 30-second `heartbeat`, not only runs with a
  work slice, so a long quiet tool is no longer settled as `owner_gone`.
- **Switching accounts starts on the new account's model.** A conversation resumed on another
  account that names a model this account cannot use starts on this account's own latest choice,
  with a notice, instead of showing and sending the old account's model. Plan and normal mode keep
  their own model and effort in the new terminal: a mode that never chose an effort starts on the
  default rather than the other mode's, a mode switch during a reply waits for it to settle, and a
  one-shot `/plan` runs on the plan mode's choice.
- **A reply whose provider request timed out and was retried successfully is now recorded as
  completed**, not failed. A terminal window whose terminal closed no longer leaves its process
  running.
- Terminal runs now record Pi's session id as `nativeSessionId`, as host runs do (in-process runs
  keep recording their history file). `/session` takes a saved conversation's session id as well
  as its file. Plugin dialogs reach the window as questions.

Behaviour changes to know about: in the default terminal, plugins get the host's interface
(dialogs, notices, status lines and text widgets); custom terminal components, key handlers,
renderers, shortcuts and themes need `XINGULAR_TERMINAL_RUNTIME=inprocess`. The prompt is
unchanged, so the provider cache is not invalidated by this release.

Not in this release: remote control (`/remote-control`) still belongs to a terminal session, so a
phone cannot reach an App chat, and a reply that outlives its window under `--daemon` loses its
phone (PAR-018). The stall guard was tested with a fake Pi session and fake timers; no live model
request exercised it.

The release workflow builds the tarball from the `v2.0.0-unstable` tag, reruns CI on Ubuntu and
macOS, smoke-tests that exact tarball on both, and attaches it with `SHA256SUMS` to the GitHub
release before publishing it to npm's `unstable` dist-tag with provenance. The published SHA-256 and
npm integrity are the ones in that attached file, which `scripts/release-verify.mjs` checks against
the registry.
